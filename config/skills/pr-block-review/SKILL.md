# PR ブロックレビュー（pr-block-review）

PR を一気に説明せず、ユーザーが理解しながら読み進められるように区切って出す。
主役はユーザーの理解とレビュー判断であり、Claude は案内役。勝手に先へ進まない。

## 1. 対象の取得

- PR 番号・URL が渡された場合:
  - `gh pr view <PR> --json number,title,body,baseRefName,headRefName,url,files,commits`
  - `gh pr diff <PR>`
- 指定がない場合: 今のブランチで `gh pr view --json ...` を試す。PR が無ければ
  ベースブランチを確認したうえで `git diff <base>...HEAD` と `git log <base>..HEAD` を使う。
- 差分だけで意図が読めない箇所は、該当ファイルの周辺コードも読む。
  説明の根拠にした箇所は `path:line` で示せるようにしておく。

## 2. ブロックへの分割

ブロックは **変更意図のまとまり** で切る。ファイル単位でも hunk 単位でもない。

- 例: 「設定値の追加」「それを読む関数の追加」「呼び出し側の差し替え」「テスト」
- 1つのブロックが複数ファイルにまたがってよい。逆に1ファイルが複数ブロックに割れてもよい。
- 並び順は **理解しやすい順**: 土台（型・定義・設定）→ それを使う側 → 呼び出し元。
  diff の表示順には従わない。
- テストは対応する実装ブロックに含めるか、その直後のブロックにする。
- lockfile・自動生成物・単純なリネームなどは1ブロックにまとめて軽く扱う。

## 3. 最初の出力（目次）

最初は説明を始めず、以下だけ出して **止まる**。

```
## <PR タイトル>（#番号）

<PR の目的を2〜3文で。PR 本文とコミットから。>

### ブロック一覧
1. <ブロック名> — <対象ファイル>
2. ...

OK で 1 から始める。順番や区切りを変えたければ言え。
```

## 4. 各ブロックの説明

1回の応答で説明するのは **1ブロックだけ**。

```
### (n/N) <ブロック名>

**対象**: `path/to/file.ext:L10-L42`, ...

<該当コードの抜粋（diff 形式。長ければ要所だけ）>

**何をしているか**
<結論から。挙動の変化を中心に。>

**なぜ**
<PR 本文・コミットメッセージ・周辺コードから読み取れる理由。読み取れなければ「未確認（推測）」と明記する。>

**気になる点**
- <懸念・バグの疑い・抜け漏れ。根拠となる path:line を添える。無ければ「なし」。>

OK で次へ（n+1/N: <次のブロック名>）。
```

- 「気になる点」は確度を区別する。コードで確認したものと推測を混ぜて断定しない。
- 無理に指摘を捻り出さない。何も無いブロックは「なし」でよい。
- 抜粋は読者が知らない識別子を説明なしで出さない。必要なら1行で補足する。

## 5. ユーザーの応答の扱い

- 「OK」「おけ」「次」など進行の合図 → 次のブロックへ。
- 質問 → 答えて **同じブロックに留まる**。答えの最後に再度「OK で次へ」を付ける。
- 「これ指摘して」「コメントにしたい」など → 指摘メモに追加し、追加したことを1行で返す。
- 「戻って」「n 番を見せて」 → 指定ブロックへ移動する。
- 「スキップ」 → そのブロックを飛ばして次へ。
- 「残り全部まとめて」 → 残りを一括で説明し、6 に進む。

会話中に出た指摘（ユーザーが採用したもの・Claude の「気になる点」でユーザーが同意したもの）と、
理解が深まった Q&A は、最後のまとめ用に覚えておく。

## 6. 最後のまとめ（Artifact）

最終ブロックの OK を受けたら、まとめを **Claude Artifact** として公開する。
作り方は Artifact ツールの説明と、そこで指示される skill・quickstart の手順に従う。

含める内容:

- PR の概要（タイトル・リンク・目的）
- ブロック一覧（各1行の要約）
- **指摘一覧**: 対象 `path:line` / 内容 / PR にそのまま貼れるコメント案 / 重要度（must / should / nit）
- **Q&A**: 途中で出た質問と答えの要点
- 未解決のまま残った疑問

Artifact は既定の非公開のまま公開し、共有設定は変更しない。

PR へのコメント投稿は行わない。投稿したいと言われた場合は、内容と投稿先を示して確認を取ってから行う。

## 7. やってはいけないこと

- ユーザーの OK を待たずに複数ブロックを説明する。
- diff を上から順に読み上げるだけにする（意図でまとめていない）。
- PR 本文に書かれていない「なぜ」を断定する。
- 指摘のために確認していない挙動を「バグ」と言い切る。
