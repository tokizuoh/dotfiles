# PR レビュー Artifact（pr-review-artifact）

PR の解説とマージ可否の総評を、Claude Artifact 1枚にまとめる。
説明は Artifact の中で完結させ、セッションの対話では行わない。

## 1. 対象の取得

- PR 番号・URL が渡された場合:
  - `gh pr view <PR> --json number,title,body,baseRefName,headRefName,url,files,commits`
  - `gh pr diff <PR>`
- 指定がない場合: 今のブランチで `gh pr view --json ...` を試す。PR が無ければ
  ベースブランチを確認したうえで `git diff <base>...HEAD` と `git log <base>..HEAD` を使う。
- 差分だけで意図が読めない箇所は、該当ファイルの周辺コードも読む。
  説明の根拠にした箇所は `path:line` で示せるようにしておく。
- PR のリポジトリが手元に無いときは、head ブランチのファイルを GitHub API で読む:
  - ファイル一覧: `gh api repos/<owner>/<repo>/git/trees/<headRefName>?recursive=1 -q '.tree[].path'`
  - 中身: `gh api "repos/<owner>/<repo>/contents/<path>?ref=<headRefName>" -H "Accept: application/vnd.github.raw"`
- `gh search code` はデフォルトブランチしか見ないので、PR で追加された識別子は見つからないことがある。
  head にしか無いものを探すときは使わない。
- `gh pr checks <PR>` で CI の結果を必ず取る。総評の根拠に使う。

## 2. ブロックへの分割

ブロックは **変更意図のまとまり** で切る。ファイル単位でも hunk 単位でもない。

- 例: 「設定値の追加」「それを読む関数の追加」「呼び出し側の差し替え」「テスト」
- 1つのブロックが複数ファイルにまたがってよい。逆に1ファイルが複数ブロックに割れてもよい。
- 並び順は **理解しやすい順**: 土台（型・定義・設定）→ それを使う側 → 呼び出し元。
  diff の表示順には従わない。
- テストは対応する実装ブロックに含めるか、その直後のブロックにする。
- lockfile・自動生成物・単純なリネームなどは1ブロックにまとめて軽く扱う。

## 3. Artifact の作成

**Claude Artifact** として公開する。
作り方は Artifact ツールの説明と、そこで指示される skill・quickstart の手順に従う。
既定の非公開のまま公開し、共有設定は変更しない。

### Artifact の構成

上から次の順に並べる。

1. PR の概要（タイトル・リンク・目的）
2. **総評**（下記）
3. ブロックごとの欄（下記）

### 総評

| 項目 | 内容 |
|---|---|
| 判定 | 「マージしてよい」「条件付きでマージしてよい」「マージを止めるべき」のどれか1つ |
| 根拠 | 判定の理由を3〜5項目。各項目に根拠ラベル（確定(ファイル)／確定(実測)／一次ソース／推測）と、`path:line`・コマンド・URL を付ける。`gh pr checks <PR>` の CI 結果と、変更の影響範囲（アプリ本体か、CI・開発ツールだけか など）を必ず含める |
| マージ前にやること | 判定が「条件付き」「止めるべき」のときだけ。やるべきことを箇条書きで書く |

- 推測を根拠にした判定は断定しない。その根拠に「未確認（推測）」と確認手段を書く。
- ブロックの「気になる点」のうちマージ判断に効くものは、総評の根拠か「マージ前にやること」に引き上げる。

### ブロックごとの欄

| 項目 | 内容 |
|---|---|
| ファイル | リポジトリルートからの相対パスと行範囲、増減した行数。変更は無いが説明の根拠にしたファイルは「参照のみ」と書いて載せる |
| 差分 | PR の diff をそのまま載せる。追加・削除・hunk ヘッダを色分けし、長い行はブロックの中で横スクロールにする。lockfile・自動生成物は差分を省き、ファイル名と増減行数だけ載せる |
| どういう変更か | 挙動の変化を結論から |
| どういう意図か | PR 本文・コミットから読み取れること。読み取れないものは「未確認（推測）」と明記する |
| 気になる点 | ブロックごとの懸念はここだけに書く。根拠の `path:line` を添え、確認したものと推測を区別する。無ければ「なし」 |
| リリースノート差分 | 依存更新の PR のときだけ足す。上げる前と後のバージョンの間のリリースノートを、一次ソース（GitHub Releases・CHANGELOG 等）の URL 付きで要約する。直接更新した依存だけでなく、lockfile で動いた推移的依存も対象にする |

- 無理に懸念を捻り出さない。
- 差分の抜粋や説明で、読者が知らない識別子を説明なしで出さない。必要なら1行で補足する。

## 4. セッションでの出力

公開後、セッションに出すのは次の2つだけ。ブロックの説明はチャットに書かない。

```
Artifact: <URL>
総評: <判定>（<結論を1行で>）
```

公開後にユーザーから質問が来たら、チャットで答えてよい。
その答えで Artifact の説明や総評が変わるときだけ、**同じ file_path で再 publish** して同じ URL の Artifact を更新する。

PR へのコメント投稿は行わない。投稿したいと言われた場合は、内容と投稿先を示して確認を取ってから行う。

## 5. やってはいけないこと

- PR 本文に書かれていない「なぜ」を断定する。
- 確認していない挙動を「バグ」と言い切る。
- 更新のたびに別の file_path で publish して、新しい URL の Artifact を作る。
