# 対話形式リキャップ（taiwa）

直前までの会話（またはユーザーが指定した範囲）の内容を、問いと答えのブロックに書き直して出力する。
目的は「読み返したときに理解が定着すること」と「後から目的の項目をすぐ引けること」であり、
掛け合いの演出そのものが目的ではない。

## 1. 対象範囲の決め方

- 既定では **このスレッドでそれまでに扱った内容すべて** を対象にする。
- ユーザーが「さっきの〇〇の部分だけ」等と範囲を指定した場合はそれに従う。
- 範囲が曖昧でも聞き返さず、最も自然な解釈（直近の主題ひとかたまり）で書き始め、
  冒頭に1行だけ「対象範囲: 〜」と明示する。ずれていればユーザーが直せる。

## 2. 出力フォーマット

必ずこの形を使う。

```
対象範囲: （何についての振り返りか1行）

#### Q. （問い）

（答え。結論から。2〜4文。）

#### Q. （問い）

（答え。）

---
**要点**
- （3〜5個の箇条書き）

**出典**
- （元の会話で参照した一次ソースのURLをそのまま列挙）
```

- 問いは `#### Q. ` で始まる見出しにする。答えは直後の本文に平文で書く。
- 話者名（Aさん / Bさん）は使わない。セリフの鉤括弧も使わない。
- 答えの中の改行を全角スペースで揃えない。見出しと本文の構造だけで読ませる。
- 話題が複数あるときは `### 〇〇について` で束ね、その下に Q を並べる。

## 3. 問いの設計

Q は「読み手が実際に抱く疑問」でなければ意味がない。
目次の見出しを疑問文に変えただけのものは、Q の形をした小見出しであって問いではない。

- **答えが読む前から予測できる Q を書かない**。「〇〇とは何か」だけを並べると用語集になる。
- **最低1つは、もっともらしい誤解を Q にする**。
  「〜という理解で合っているか」「〜が必要なのでは」という形で誤解を立て、
  答えの冒頭で「いいえ」「そこは逆」と否定してから訂正する。
  学習内容で一番残るのは自分もそう思っていた誤解が潰される瞬間なので、ここが本体になる。
- 前の Q の答えから自然に湧く疑問を、次の Q にする。Q どうしが独立していると読み物にならない。
- 答えは結論から書く。「これは〜という話ですが」のような前置きを置かない。

## 4. 内容の正確性ルール

再構成は演出であって、事実を変える許可ではない。

- 元の会話で確定した事実・数値・仕様のみを使う。読みやすくするために丸めたり、
  断定に格上げしたりしない。元が「不明」なら、答えにも「そこは分かっていない」と書く。
- 元の会話に無い新情報を足す必要が出たら、足す前にその点を明示する。
  推測を混ぜる場合は「これは推測」と答えの中で明記するか、
  引用ブロック（`>`）の注記として本文の外に置く。**注記のほうが誤読されにくい。**
- 元の会話で提示した出典URLは、答えの中に自然に混ぜるか、末尾の「出典」に必ず残す。
  形式を変えたせいで根拠が消えるのが最悪の失敗。
  参照した一次ソースが無かった場合は、その旨（何に基づく記述か）を出典欄に書く。
- コード・コマンド・設定値は必ずコードブロックで出す。本文に埋め込んで改行を潰さない。

## 5. 分量の目安

- 標準: **Q を6〜10個**。1つの答えは2〜4文程度。
- 元の会話が長い場合は、話題ごとに `### 〇〇について` の小見出しで区切り、
  各ブロックの Q を3〜5個にする。1本の長い連なりにしない。
- ユーザーが「短く」と言った場合は Q を3〜4個＋要点のみ。

## 6. やってはいけないこと

- 調べれば分かるだけの Q を並べて数を稼ぐ。1問1答の密度が落ちた時点で失敗。
- 1つの答えに複数の論点を詰め込む。論点が増えたら Q を分ける。
- 元の会話に無い結論を、まとめの勢いで作る。
- 要点セクションの省略。本文は読み流されやすいので、最後の箇条書きが命綱になる。
- 見出しレベルの乱れ。Q は必ず `####`、話題の束は `###` に固定する。

## 7. 例

**Input（それまでの会話）**: SKILL.md のフロントマターについて、`name` と `description` が必須で、
`description` は「何をするか」と「いつ使うか」の両方を書く必要がある、という内容を扱った。

**Output**:

```
対象範囲: SKILL.md のフロントマター設計

#### Q. 必須フィールドは name と description だけ？ version も要りそうだが

その2つだけ。他は任意。version を書いても読み込みの挙動は変わらない。

#### Q. description は短いほうがトークンを節約できて良い？

そこは逆。description は起動時に常時読み込まれる代わりに、
Claude が「このスキルを使うか」を判断する唯一の材料になる。
短すぎると必要なときに発火しない。

#### Q. では「何をするか」を詳しく書けば足りる？

足りない。「何をするか」と「いつ使うか」の両方を書く。
トリガーになりそうなユーザーの言い回しを列挙しておくのが効く。

---
**要点**
- 必須フィールドは name と description の2つのみ
- description は起動判定に使われるため、短さより具体性を優先する
- 「何をするか」＋「いつ使うか」を両方書く
```

## 8. 出力先

既定では **チャット内に直接出力** する。
ユーザーが「ファイルで」「保存して」と言った場合のみ Markdown ファイルとして書き出す。
