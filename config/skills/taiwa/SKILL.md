# 対話形式リキャップ（taiwa）

直前までの会話（またはユーザーが指定した範囲）の内容を、2人の掛け合いに書き直して出力する。
目的は「読み返したときに理解が定着すること」であり、雑談風の演出そのものが目的ではない。

## 1. 対象範囲の決め方

- 既定では **このスレッドでそれまでに扱った内容すべて** を対象にする。
- ユーザーが「さっきの〇〇の部分だけ」等と範囲を指定した場合はそれに従う。
- 範囲が曖昧でも聞き返さず、最も自然な解釈（直近の主題ひとかたまり）で書き始め、
  冒頭に1行だけ「対象範囲: 〜」と明示する。ずれていればユーザーが直せる。

## 2. 出力フォーマット

必ずこの形を使う。

```
対象範囲: （何についての対話か1行）

Aさん「（問いかけ・素朴な疑問）」
Bさん「（回答・解説）」
Aさん「（掘り下げ／言い換え確認／反論）」
Bさん「（訂正・補足・具体例）」
...

---
**要点**
- （3〜5個の箇条書き）

**出典**
- （元の会話で参照した一次ソースのURLをそのまま列挙）
```

- 話者名の既定は `Aさん` / `Bさん`。ユーザーが名前を指定したらそれを使う。
- セリフは必ず `「」` で囲む。地の文（ト書き）は原則使わない。読みづらくなる。
- 3人以上は既定では使わない。指定された場合のみ増やす。

## 3. 役割設計

2人は対等ではなく、**役割を非対称にする**。これをやらないと「そうですね」「なるほど」の応酬になって情報量がゼロになる。

- **Aさん = 学ぶ側**: 初学者〜中級者。素朴な疑問、用語の確認、
  「つまり〇〇ってことですか？」という言い換え、そして **もっともらしい誤解** を担当する。
- **Bさん = 説明する側**: そのトピックを実務で扱っている人。
  Aさんの誤解を否定ではなく訂正で返し、具体例・境界条件・「実際にはこう書く」を出す。

会話全体で **最低1回は、Aさんの誤解をBさんが訂正する往復** を入れる。
学習内容で一番残るのは「自分もそう思っていた誤解が潰される瞬間」なので、ここが本体になる。

## 4. 内容の正確性ルール

対話は演出であって、事実を変える許可ではない。

- 元の会話で確定した事実・数値・仕様のみを使う。対話にするために丸めたり、
  断定に格上げしたりしない。元が「不明」なら、Bさんも「そこは分かっていない」と言う。
- 元の会話に無い新情報を足す必要が出たら、足す前にその点を明示する。
  推測を混ぜる場合は、セリフ内で「これは推測ですが」と言わせるか、
  対話の外に注記を置く。**地の文の注記のほうが誤読されにくい。**
- 元の会話で提示した出典URLは、対話中に自然に混ぜるか、末尾の「出典」に必ず残す。
  対話形式にしたせいで根拠が消えるのが最悪の失敗。
- コード・コマンド・設定値は、対話の中でもコードブロックで出す。
  セリフの中に埋め込んで改行を潰さない。

## 5. 分量の目安

- 標準: **6〜10往復**。1セリフは2〜4文程度。
- 元の会話が長い場合は、話題ごとに `### 〇〇について` の小見出しで区切り、
  各ブロック4〜6往復にする。1本の長い対話にしない。
- ユーザーが「短く」と言った場合は3〜4往復＋要点のみ。

## 6. やってはいけないこと

- 相槌だけのセリフで往復数を稼ぐ（「なるほど！」「そうなんですね！」だけの行）。
- Bさんが一方的に長い講義をして、Aさんが「はい」しか言わない。それはもう対話ではない。
- キャラ付けの過剰化（口癖、絵文字の多用、無関係な雑談）。読みたいのは中身。
- 元の会話に無い結論を対話の勢いで作る。
- 要点セクションの省略。対話は読み流されやすいので、最後の箇条書きが命綱になる。

## 7. 例

**Input（それまでの会話）**: SKILL.md のフロントマターについて、`name` と `description` が必須で、
`description` は「何をするか」と「いつ使うか」の両方を書く必要がある、という内容を扱った。

**Output**:

```
対象範囲: SKILL.md のフロントマター設計

Aさん「フロントマターって name と description だけでいいんですか。version とか要りそうですが」
Bさん「公式ドキュメント上の必須は name と description の2つだけです。他は任意です」
Aさん「じゃあ description は短いほうがトークン節約になって良い、と」
Bさん「そこは逆です。description は起動時に常時読み込まれる代わりに、
　　　Claude が『このスキルを使うか』を判断する唯一の材料になります。
　　　短すぎると必要なときに発火しません」
Aさん「つまり、何をするかだけ書けば足りない、ということですか」
Bさん「はい。『何をするか』と『いつ使うか』の両方を書きます。
　　　トリガーになりそうなユーザーの言い回しを列挙しておくのが効きます」

---
**要点**
- 必須フィールドは name と description の2つのみ
- description は起動判定に使われるため、短さより具体性を優先する
- 「何をするか」＋「いつ使うか」を両方書く
```

## 8. 出力先

既定では **チャット内に直接出力** する。
ユーザーが「ファイルで」「保存して」と言った場合のみ Markdown ファイルとして書き出す。
